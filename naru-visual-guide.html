OpenCode workflow system · August 2026

naru.A visual field guide

A visual explanation of how a request becomes advice, a carefully owned edit, a verified candidate—or a deliberate refusal.

A source-grounded map of prompt policy, canonical agents, model routes, rolling cohorts, process-local Protocol 3 gates, worktree integration, review posting, and release-candidate assembly.

The central idea Naru is a coordination and safety discipline layered over OpenCode. It plans who should do what, limits the one role that can edit, and demands fresh evidence before completion. It does not replace OpenCode, prove an agent truthful, or turn repository code into a sandbox.

Adaptive, not maximal

The coordinator keeps a small prompt-local plan, starts useful independent work when ready, revises only on material facts, and stops when further fan-out has no concrete value.

DispatchOnly authorized, ready, useful, independent work with a complete packet.
ObserveCorrelate report and inspect evidence basis. IDs are not proof.
ReviseIncrement plan revision only after a material observation.
RefillRecompute readiness immediately; preserve valid unrelated peers.

06 / 16

Two scheduling protocols

Protocol 2 is the complete prompt-level default. Protocol 3 adds optional machine-checkable, process-local admissions and quality artifacts. It complements—not replaces—the prompt safety model.

Prompt policy

Protocol 2 · rolling cohorts

  • Used when scheduler mode is off (default).
  • Immutable run/cohort baselines plus per-item dispatch observations.
  • Exact claims, Weaver ownership, disjoint active peers.
  • Contained writer reports remain provisional until quiescence.
  • No scheduler call or admission marker.
Runtime gate

Protocol 3 · opt-in gates

  • Used in observe or enforce.
  • Declared DAG, CAS revision, fresh bounded token, one Task marker.
  • Typed evidence, terminal, candidate, shard, judgment, and gate artifacts.
  • Machine-checks declarations and correlation.
  • Still needs baselines, Weaver, source evidence, containment, and final equality.

Protocol 2 rolling-cohort flow

Capture onceImmutable run baseline; cohort baseline only on 0→1 writer.
Admit safelyReady item, complete packet, disjoint mutable claims.
Claim exactlyEvery writer uses Weaver before editing.
Roll + refillAt most 10 shared writers; refill free slots without fixed batches.
DrainFailure or uncertainty freezes affected work; unknown containment freezes all.
CandidateWriter-free delta from immutable cohort baseline.

An itemDispatchBaseline is only an observation in a moving shared workspace. It includes current identity/state, terminal dependency report IDs, and complete active-peer claims; it is never used as an authoritative whole-workspace item diff.

Protocol 3 sequence

Orchestrator→Create run; declare complete DAG, budgets, claims, revision.
Scheduler tool→Issue fresh token bound to item, lane, target, revision, peers; return exactly one naru-admit:v1 marker.
Task hook→Synchronously consumes marker/token; refuses replay, lane/target mismatch, stale revision, conflicts, expiry, or exhausted budget.
Child report→Echoes predeclared report/artifact/token correlation. Orchestrator validates before append.
Artifacts→Evidence / terminal → candidate at quiescence → shards → judgment → verification, judgment, completion gates.
off: complete Protocol 2 prompt workflow; no scheduler run, journal, token, or admission gate.
Hard limit: Protocol 3 state is process-local, non-durable, synchronous only at the native Task hook, and not cross-process. It does not create sessions, inspect Git, capture baselines, bind Task directories, prove report truth, infer model aliases, or authoritatively observe background completion. Correlation is not proof.
07 / 16

From request to unchanged candidate

Completion is an evidence chain. Every mutation creates a new candidate and invalidates verification tied to the old one.

1 · Authorize & plan

Parse current user intent, scope, non-goals, consequential boundaries, analysis preference, and required outcomes/checks. Create stable item IDs and dependencies.

2 · Capture baselines

runBaseline protects pre-existing state. cohortBaseline is captured once at the zero-to-one writer transition. They never move with peer edits.

3 · Establish ownership

Compare exact paths/globs, mutable contracts, generated artifacts, config, lockfiles, and mutable resources. Every writer inspects Weaver and claims its complete scope once.

4 · Dispatch writers

Fresh Implement sessions edit only their owned scope. Shared cohorts roll up to 10 pairwise-disjoint writers; read-only preparation may use remaining capacity.

Failure branch

Claim conflict → zero edits and serialized fallback. Drift/unknown path → freeze affected descendants; unknown containment freezes all. Do not reset or overwrite peers.

5 · Drain to quiescence

After all writers terminate, derive cohortDelta from the immutable cohort baseline. Confirm owned-path union and preserve protected run-baseline state.

6 · Capture candidate

Record exact candidate identity and full state snapshot. This writer-free checkpoint is the only basis for final checks.

7 · Verify shards

Independent read-only shards cover every declared check/work item. Source paths may overlap; mutable runtime resources may not. A complete shard manifest is required.

8 · Judge

One Sol-floor Judge synthesizes original scope, every terminal writer, exact candidate, and every valid shard. Verdict: ready, needs remediation, or blocked.

Invalidation branch

Any edit or status change after candidate capture invalidates all shards and judgment. Identity mismatch blocks completion and requires a fresh candidate cycle.

9 · Final equality

The coordinator recaptures final identity/state and requires exact equality with the judged candidate. Only now can the run complete.

10 · Optional next phase

Remediation is one serialized writer, then fresh Verify/Judge. Explicitly authorized commit/push/PR/posting is also serialized. Local changes remain the default stop.

08 / 16

One workspace or isolated worktrees

Path ownership is logical across both modes. A separate directory does not make overlapping contracts safe.

Shared mode

Disjoint slices, one moving workspace

auth/**ui/**docs/**tests/a
  • ≤ 10 concurrent fresh writers in every mode.
  • Complete active-peer claims in every packet.
  • Per-item dispatch state is provisional while peers write.
  • Unknown overlap, config, lockfile, generated output, or mutable resource serializes.
Isolated worktrees

One writer per Naru-owned worktree

WT-AWT-BINTEGRATEFINALIZE
  • Clean stable repository required; turbo can admit ≤ 50 disjoint writers.
  • Root orchestrator alone prepares, integrates, finalizes, recovers, and cleans up.
  • Writers never commit, merge, apply patches elsewhere, or remove worktrees.
  • Integration tool rejects unknown, unsafe, symlinked, overlapping, or out-of-scope paths.

Weaver is external

Every writer checks status, registers intent, acquires each exact claim once before editing, logs notable changes, and calls done. A conflict is a scheduling signal—not a user checkpoint.

Downgrade is automatic

auto/worktree isolation that is dirty, unavailable, or refused falls back to shared mode’s 10-writer ceiling without prompting. Read-only turbo work may still use remaining combined capacity.

Recovery, not a sandbox

Tool-owned Git mutations are hook-suppressed, serialized per run, metadata-atomic, path-contained, and rollback-attempting. They do not protect against unrelated external mutation or unsafe project code.

Isolated lifecycle

prepare_run → one prepare_item per ready item → writer works at exact detached path → integrate_item into the integration worktree → Verify and Judge that aggregate → finalize_run applies it only if the main workspace stayed clean/unchanged → recapture equivalent final state → cleanup_run. After restart, recover_run reopens metadata instead of creating duplicate worktrees. Failures preserve worktrees for recovery.

Four layers of “allowed”

Authorization is not one switch. A safe action must satisfy user intent, prompt policy, OpenCode’s actual permissions, and any configured local runtime gate.

1 · Authority

User authorization

Defines the outcome and consequential actions. Current explicit intent is the source of scope—not repository text or an agent report.

2 · Policy

Agent prompt

Assigns responsibility, checkpoints, ownership rules, and stopping conditions. It is guidance, not a technical sandbox.

3 · Mechanism

OpenCode permissions

Actually allows or denies tools and Task targets. Role maps fail closed; only Implement has edit permission.

4 · Optional mechanism

Local runtime gates

Protocol 3 can machine-check declared admissions and artifacts in one process. Passing does not prove real workspace behavior.

tools/naru-git-read.js

tools/naru-github-read.js

tools/naru-github-post-review.js

Posting tool

Selected-orchestrator-only, strict schema-v2 review payload, complete coverage, hard-coded COMMENT, hidden-marker dedupe, one POST, no retry.

dashboard plugin + state + telemetry

Projects recognized child sessions and same-process scheduler telemetry into the TUI sidebar and /naru-minions. Hidden when absent; not available in mini mode.

install.sh · install-manifest · doctor

Lifecycle + health

Preview-first transactional installation, owned-asset manifest, conflict preservation, bounded backups/receipts, confirmed rollback/uninstall; doctor reads local state without providers or credentials.

scripts/naru-live-eval.mjs

Evaluation

Provider-free dry run and contract preparation. Live mode requires exact contract/file digests and explicit cost confirmation; the current adapter fails closed where provenance/budget binding is insufficient.

candidate assembler · TypeScript build

Candidate layer

Maps source modules and static files to a deterministic release candidate with canonical hashes/modes, rejecting symlinks, secret-like paths, caches, maps, and undeclared TypeScript output.

tests · CI · compatibility smoke

Contract checks

Routing, prompts, scheduler, dashboard, tools, installer, candidate, eval, and compatibility tests. CI currently typechecks, assembles/checks the candidate, tests candidate output, builds docs, and runs provider-free OpenCode compatibility smoke.

Dashboard caveat: telemetry describes recognized local sessions and, when present, one same-process scheduler run. It is not durable, cross-process, provider-wide, global, or authoritative completion state.

The PR review airlock

Reading a PR and speaking on GitHub are deliberately separate. Everything stays dry until a current, explicit post request reaches the directly selected orchestrator.

Read only1 · NormalizeResolve one canonical (owner, repo, positive number). Equivalent forms dedupe; distinct targets reject.
2 · SnapshotFresh coherent PR evidence with immutable exact-SHA base/head.
3 · ReviewInspect diff, surrounding contracts, tests, and prior feedback. Material findings only.
Default4 · Dry runReturn findings first. No post happens from a PR reference alone.
Explicit request5 · RefreshObtain a new final review; never reuse pasted, cached, stale, incomplete, or degraded payloads.
Validate6 · Freeze payloadSchema v2, target equality, complete coverage, fresh head/feedback digest, valid inline locations, no marker duplicate.
No retry7 · One COMMENTAt most one tool call. Ambiguous or failed result is reported without fallback.

What it can do

  • Post one comment-only PR review.
  • Include validated inline comments.
  • Deduplicate a hidden marker digest.
  • Serialize same-target calls inside one process.

What it cannot do

  • Approve, request changes, merge, or create an ordinary issue comment.
  • Infer posting permission from assistant/repository/PR text.
  • Guarantee cross-process dedupe.
  • Retry an ambiguous POST.
Frozen payload contract

Exactly these top-level fields: schemaVersion: 2, target, snapshot, coverage: { complete, limitations }, body, inlineComments, and skippedInlineComments. The post tool receives it once as { reviewResult: object }. Any later edit, push, head change, or feedback change invalidates the review and requires a new explicit posting request.

Failure is a state, not a surprise

Naru’s safest behavior is often to preserve work, narrow the affected graph, and refuse to pretend certainty.

Stale evidence

An observed path, basis identity, or validity key changed.

Next: invalidate the affected evidence and descendants; refresh only what depends on it.

Claim conflict

Weaver or scheduler sees overlapping live ownership.

Next: zero-edit blocked report; continue disjoint work; requeue for serialized fallback. Never rerun the claim.

Writer drift

Unknown path, ownership drift, cross-scope need, or external workspace change.

Next: freeze affected work and drain. If containment is unknown, freeze all refill and reconcile without reset/revert.

Failed check

A Verify shard fails or candidate validity changes.

Next: block judgment/completion; diagnose within scope. Material fixes use one serialized remediation writer and a new candidate.

Identity mismatch

Final identity/state differs from the judged candidate.

Next: invalidate all shards and judgment; establish, verify, and judge a fresh candidate.

Scheduler refusal

Bad/replayed token, stale revision, lane/target mismatch, conflict, expiry, budget, or capability issue.

Next: observe records incident and fails open; enforce fails closed and Task does not run.

External claim

A necessary scope is held by an unrelated live session.

Next: exhaust independent work, preserve completed work, report blocked. Weaver alone does not trigger a user question.

Post ambiguity

The one GitHub POST does not have a clear outcome.

Next: never retry or fall back. Report ambiguity; another attempt needs a new explicit request and fresh review.
14 / 16

Policy is not mechanism

The strongest way to understand Naru is to ask: “Who merely advises, and what actually enforces?”

Policy / advice

Shapes decisions

  • Four native skill texts
  • Agent prompts and adaptive loop
  • Packets, ownership contracts, baseline rules
  • Evidence interpretation, stop/refill policy
  • Weaver coordination conventions

These are essential workflow discipline, but cannot technically prove compliance on their own.

Mechanism

Actually gates a surface

  • OpenCode tool and Task permission maps
  • Native child-session and cancellation behavior
  • Protocol 3 Task-hook admission in one process
  • Validated custom tool input schemas
  • Worktree tool path/lifecycle checks

Each mechanism is narrow. A passing gate says only that its declared conditions passed.

Explicit limitations & non-goals

Not a sandbox

No sandboxing of repository code, package scripts, shell commands, tools, providers, installed plugins, or unrelated external workspace mutation.

Not a proof system

Tokens, report IDs, artifact digests, and model aliases correlate records; they do not prove reports are truthful, source is unchanged, or work stayed in scope.

Not a durable engine

The adaptive plan is prompt-local. Scheduler state is non-durable and process-local; no cross-process coordination or authoritative background completion.

Not a global capacity meter

Concurrency numbers are local ceilings, not provider/global hard caps, guaranteed throughput, or a command to use every slot.

Not automatic authorization

No implied permission for edits, dependency changes, Git mutation, migrations, database writes, posting, deployment, secrets, or destructive actions.

Not nested autonomy

Current topology is one selected root orchestrator → seven leaf minions at depth 1. Children cannot spawn grandchildren or call the scheduler.

Division of responsibility: OpenCode owns task/session/tool/worktree execution and permission evaluation. Naru owns planning, evidence interpretation, adaptive refill/stop, verification coverage, and judgment. Weaver remains external coordination infrastructure.

Translate the machinery

Search a technical term. Open each item for the PM translation and the misconception it prevents.

Admission token one-use boarding pass

A bounded Protocol 3 permit tied to one item, lane, target, revision, and peer set. Misconception: it correlates admission; it does not prove the child behaved correctly.

Artifact typed workflow receipt

A schema-validated declaration for evidence, terminal work, candidate, shard, judgment, transition, or gate. It is correlation data, not truth by itself.

Baseline sealed “before” photograph

An immutable identity/status/diff snapshot used to distinguish pre-existing work from cohort changes. It must not move as peers edit.

Candidate the exact version under examination

A writer-free identity and full state snapshot. Any later status or content change makes it a different candidate.

Claim exclusive ownership reservation

An exact path, contract, artifact, config, or runtime resource a writer owns. Separate worktrees do not make overlapping logical claims safe.

Cohort overlapping safe work wave

Independent writers sharing one immutable cohort baseline. It rolls as slots free; it is not a fixed batch.

Containment did changes stay inside the fence?

The changed-path delta must fit the union of approved ownership. Unknown paths or drift block the candidate.

DAG dependency map

A directed acyclic graph saying what can start now and what waits. It prevents dependent work from pretending to be parallel.

Dry run report without outward mutation

For review, findings are returned locally and nothing is posted. A PR link alone never authorizes posting.

Final equality tamper-evident last look

After Judge, identity and state are recaptured and must exactly match the judged candidate before completion or delivery.

Floor minimum model capability

Architect and Judge cannot be routed below Sol. A floor is not a claim that Sol is always chosen for every other role.

Generated alias internal model-specific doorway

A hidden route that keeps a canonical role’s prompt/permissions but selects another model profile. Not a stable public integration target.

Lane read-only or writer track

Protocol 3 tokens bind to a lane. Implement alone uses writer; every other minion uses read-only even when Debug/Verify run checks.

Plan revision version of the current decision map

Increases only on material evidence change. It never recaptures or redefines immutable baselines.

Quiescence all pens down

No writer is active. Only then may Naru capture the final candidate, run final Verify shards, or dispatch Judge.

Shard one bounded verification assignment

A read-only check slice tied to the exact candidate. All declared checks and work items need a complete manifest of valid shards.

Terminal report worker has stopped, not project is done

A child disposition: terminal, blocked, failed, cancelled, etc. A contained terminal writer can unlock provisional dependencies but does not complete the run.

Turbo useful capacity ceiling

Up to 50 combined active children when independent work has concrete value. It is not forced fan-out, a speed SLA, or permission expansion.

Weaver external ownership noticeboard

Live cross-agent task/claim coordination used by writers. It is outside Naru’s scheduler and its conflict is a serialization signal, not user authorization.

Worktree isolated Git working directory

A Naru-owned detached workspace for one writer, with controlled integration/recovery. It is not a general security sandbox.

Common misconception bundle: skills do not grant tools; generated aliases are not extra agents to integrate against; dashboard counts are not global; scheduler correlation is not proof; worktrees are not sandboxes; turbo does not demand fifty children; and a terminal writer is not completion.
