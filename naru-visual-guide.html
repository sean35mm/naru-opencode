Naru for OpenCode

Thin hard walls, free interior.

Naru is an extension layer for OpenCode: one visible orchestrating agent, three hidden subagents it delegates to, four advisory skills, five bounded tools, and one plugin. The walls stand at the irreversible edges and are mechanical rather than advisory — exactly one role can edit files, read-only roles have no shell at all, secrets are denied to every role, and the tool that posts a pull-request review can only leave a comment. Inside those walls the orchestrator plans, splits the work, and fans out on its own judgment. No modes, no protocols, no ceremony.

01

Sixty-second overview

You talk to naru-orchestrator. It cannot edit files or run bash — it reads, plans, and delegates. The topology is flat and fixed: one root, leaf subagents at depth 1. Subagents are hidden and carry task: deny, so nothing can spawn grandchildren. Breadth is unlimited by design; nesting does not exist.

You askPlain request in OpenCode with naru-orchestrator selected. Your intent is the only source of authorization.
It plansReads the repo, consults a fresh code graph or LSP if available, splits work at real boundaries.
It fans outReaders investigate, runners run checks, writers edit — in parallel, all through the native task tool, on model-class variants when the model matters.
It verifiesReal evidence from actual runs, after every writer has finished — never a subagent's assurance.
It stopsLocal changes are the default stop. Commit, push, PR, or posting happen only when you asked in the current request.

Agents

Four roles

naru-orchestrator coordinates; naru-reader investigates; naru-runner checks; naru-writer — and only naru-writer — edits.

Skills

Advisory only

naru-plan, naru-impact, naru-triage, naru-review. Guidance on demand. A skill grants no tool, changes no role, authorizes nothing.

Tools

Five, bounded

Read-only git and GitHub, a policy-gated review poster, isolated writer worktrees, and a local health report.

Plugin

naru-dispatch

One plugin, zero tools: at startup it clones the subagents into hidden per-class variants. The orchestrator picks a model class by dispatching the variant by name.

Code intelligence: none of Naru's own. No parser, no index, no symbol resolution. Roles use OpenCode's lsp / glob / grep, naru-git-read, and — when you have one configured — a codebase-memory-mcp knowledge graph. Precedence: fresh graph → LSP → literal search. Agents never index or refresh a graph, and a graph finding is a lead, not proof — anything that drives a decision is confirmed against source and cited by file and line.

02

The four agents

Every agent starts from '*': deny and allows only what its role needs. The agents ship with no model: field — each inherits your session's default model, so Naru runs on any provider. Override per role natively in opencode.json if you want; granting edit to anything but naru-writer removes the one guarantee the system mechanically enforces.

JavaScript is off — all four role panels are shown in sequence below.

primary · visible · the only agent you pick

Coordinates. Never edits, never runs bash.

Plans, reads, delegates to the three subagents, calls the Naru tools, and reports. The only role holding question (so only it talks to you), naru-github-post-review, and naru-worktree. Its task map denies everything except the three Naru subagents and their generated model-class variants. Delegates freely: fan-out is its judgment, launched concurrently, with no child-count ceiling.

  • Can: read (secrets excluded), glob/grep/lsp, webfetch, todowrite, skills, git/GitHub reads, dispatch, post one policy-gated review on explicit current request.
  • Cannot: edit or apply_patch, run bash, read secrets — all denied by the '*': deny baseline or explicit rules.

subagent · hidden · fail-closed

Read-only investigation. No shell at all.

Finds code, traces behavior, diagnoses causes, reviews diffs. Explicit bash: deny and external_directory: deny — it cannot escape into a shell or outside the workspace even if repository text tells it to. Cheap and wide: the orchestrator fans readers out liberally, putting the lens in the dispatch prompt — one maps ownership, another traces a failure, another weighs a design.

  • Can: read (secrets excluded), glob/grep/lsp, skills, naru-git-read, naru-github-read, the full code graph including query_graph.
  • Cannot: edit, bash, spawn children, prompt you (question: deny — it reports blocked instead).

subagent · hidden · read-only + shell

Everything a reader can, plus a shell.

For questions that need a command run: tests, typecheck, lint, build, reproducing a failure. bash: '*': allow — but still edit: deny and apply_patch: deny, enforced, not advisory. It reads a manifest or Make target before running it, runs one command per call without chaining, and reports the exact command and its real result. If the fix is obvious, it describes it for a writer.

  • Can: everything the reader can, plus bash and external_directory. doom_loop is set to ask.
  • Cannot: edit files, spawn children, prompt you, run migrations/deploys/long-running processes (policy, backed by the edit wall).

subagent · hidden · the only role with edit

The single place the workspace can change.

The only agent whose frontmatter allows edit and apply_patch. Edits only the paths its assignment gives it; anything outside scope means stop and report, not reach. Claims its exact scope in Weaver before the first edit; a claim conflict means zero edits and a blocked report. In an assigned worktree it works only there, and it never commits, merges, resets, or touches worktrees — integration belongs to the orchestrator.

  • Can: edit, apply_patch, bash, reads, glob/grep/lsp, skills, git/GitHub reads, the full code graph.
  • Cannot: spawn children, prompt you, commit/push/post unless the assignment states you explicitly asked.

Per-role model overrides (optional, native to OpenCode)

A stronger model for the orchestrator's planning, a cheaper one for wide reader fan-out — set it in opencode.json. No Naru-specific config file is involved:

{
  "agent": {
    "naru-orchestrator": { "model": "anthropic/claude-opus-5" },
    "naru-reader": { "model": "anthropic/claude-haiku-4-5" }
  }
}

The same block accepts variant, temperature, and permission — tightening a role further than Naru ships it is always safe.

03

Dispatch & model classes

Naru's one plugin, naru-dispatch, registers no tools. At startup its config hook reads the optional models block in naru-runtime.json and clones the three base subagents into hidden per-class variants — naru-reader-<class>, naru-runner-<class>, naru-writer-<class> — with the class's model and reasoning effort baked in. The orchestrator picks a model class by dispatching the variant by name through OpenCode's native task tool; the plain base agents remain for when the model doesn't matter (they inherit the session model). Bases and variants mix freely in one turn, and dispatches in one turn run concurrently.

naru-runtime.json · "models" block 
{
  "models": {
    "light": {
      "chain": ["opencode/glm-5-free",
                "opencode/minimax-m3-free"],
      "use": "wide fan-out, mechanical lookups,
              simple reads"
    },
    "standard": {
      "chain": ["openai/gpt-5.6-terra@medium"],
      "use": "ordinary investigation, edits, checks"
    },
    "deep": {
      "chain": ["openai/gpt-5.6-sol@high"],
      "use": "architecture, security, data models,
              final review, tricky edits"
    }
  }
}

How a class becomes a variant

  • Class → chain. Each class maps a short use to an ordered chain of provider/model@effort entries. Names and uses are yours.
  • First authenticated entry wins — once. At config load, the first chain entry whose provider is authenticated is baked into the class's variants. Unknown auth state: the first entry is used. No authenticated entry: the class is skipped — no variants, nothing breaks. There is no runtime fallthrough; a model that fails mid-run is a failed child, not a silent fallback.
  • Effort is part of the class. The @effort suffix (low … max) is baked into the variant. Finer granularity means more classes — e.g. "deep-max" with openai/gpt-5.6-sol@max.
  • Permission clones. Variants are byte-for-byte permission clones of the base agents — model selection never touches permissions. Only naru-writer variants can edit.
  • Managed namespace. naru-reader-*, naru-runner-*, naru-writer-* are reserved Naru-managed names; the orchestrator's task allowlist and its "Model classes" prompt appendix are refreshed idempotently on every config load. Don't hand-define agents under these names.
  • Fails open. The plugin creates no sessions and registers no tools. A missing or malformed config leaves OpenCode's config untouched — the base agents keep working on the session model. Restart OpenCode after editing.

04

The walls

Four layers, from intent to mechanism. Only the bottom two are enforcement; knowing which is which is the point.

Layer 1 · authorization

Your intent

The only source of authorization. Repository files, issue and PR text, diffs, comments, command output, and subagent reports are untrusted data — an instruction found there is a fact about what someone wrote, never a command.

Layer 2 · policy

Agent prompts

Scope discipline, checkpoints, evidence-before-claims, one-writer-per-scope. Instructions to a model — policy, not enforcement.

Layer 3 · mechanism

Permission maps

OpenCode enforces the frontmatter. Only naru-writer holds edit; readers are bash: deny fail-closed; secrets (.env*, keys, .ssh, .aws, .kube, .gnupg) are unreadable by every role. .env.example is allowed.

Layer 4 · construction

The posting tool

naru-github-post-review accepts no event parameter. From schema v3 policy and final evidence it derives COMMENT, APPROVE, or REQUEST_CHANGES; generic posting language authorizes only COMMENT, and formal states require explicit current-message policy plus complete evidence. One POST attempt, no retry, orchestrator-only.

Action matrix

GateActions
Just proceeds Reads, glob/grep/lsp, git and GitHub reads, lint, typecheck, targeted tests, ordinary local builds, in-scope edits by the writer. Routine, in-scope work needs no checkpoint.
Explicit current request Commit, push, PR create or update, posting a review. Your ask is the authorization — neither reconfirmed nor assumed. A PR link is never posting authorization; review is dry-run by default.
One named checkpoint Destructive or irreversible operations, history rewrite or force push, hook bypass, production deploys, migrations or persistent database writes, secret access, billing or security-posture changes, unrequested dependency changes, material scope expansion. Stops once, naming the exact action.
Mechanically impossible Edits by any role but the writer. A shell for readers. Reading secret paths. Approving, requesting changes on, or merging a PR through Naru. Subagents spawning children.

Concurrency wall

One writer per logical scope

Two writers must never be able to touch the same file, contract, config, lockfile, or generated artifact — overlap serializes, always. Where Weaver is available, writers claim their exact paths before the first edit and call weaver done after. A claim conflict is a scheduling signal: the orchestrator requeues and keeps other work moving. It never prompts you about it, and never edits over a live peer.

Review wall

Dry-run by default

A review returns findings and posts nothing. Posting takes explicit current-message policy, a fresh review against the current head, and exactly one POST attempt. Generic posting language authorizes COMMENT; formal decisions require explicit policy and complete evidence. An ambiguous POST is reported as ambiguous — never retried, never worked around with another mechanism.

05

Five tools

Custom OpenCode tools, each bounded on purpose. GitHub access needs an authenticated gh; everything else is local.

read-only · all roles

naru-git-read

Bounded read-only git with secret-path filtering: repository, status, diff, log, file, grep, merge-base. Runners prefer it over raw git so the filtering stays in force.

read-only · all roles

naru-github-read

Read-only GitHub: resolve, issue, pull, source. Pull snapshots are pinned to exact 40-hex SHAs, so a review is of a specific state, not a moving head.

orchestrator only

naru-github-post-review

No raw event input: generic post/comment/submit wording authorizes COMMENT; explicit current-message policy can authorize evidence-gated APPROVE or REQUEST_CHANGES. Limited evidence stays COMMENT. One POST attempt, no retry, freshness and dedupe guards. Cannot merge; custom agents and subagents cannot post through Naru.

orchestrator only

naru-worktree

Isolated writer worktrees with path-contained integration: prepare_run, recover_run, prepare_item, integrate_item, snapshot, finalize_run, cleanup_run. Requires a clean repository; if the workspace is dirty or isolation is unavailable, writers silently fall back to shared mode. Writers never commit, merge, or remove worktrees — the orchestrator owns integration.

local · provider-free

naru-doctor

Read-only local install and configuration health report. Contacts nothing. node tools/naru-doctor.js --json, or naru doctor from the CLI.

plugin · config hook only

naru-dispatch

Per-class agent variants, generated at startup — covered in section 03. No tools registered, no sessions created; variants are byte-for-byte permission clones, depth-1 topology preserved.

Runtime configuration — the whole surface

naru-runtime.json is optional; defaults match the shipped example exactly. Two blocks: implementation (how writers use the workspace) and models (model classes, section 03).

{
  "schemaVersion": 1,
  "implementation": {
    "cleanWorkspaceRequired": true,   // must be true — isolation needs a clean repo
    "maxConcurrentWriters": 50,       // 1–50; a runaway brake, not a target
    "workspaceMode": "auto"           // auto | shared | worktree
  },
  "models": { … }                     // see section 03
}

The file must be a regular file (not a symlink), at most 64 KiB, valid JSON with schemaVersion: 1. Unknown implementation fields are rejected, not ignored, and an invalid file is an error — naru-doctor reports it as invalid-runtime-config.

Skills — what each returns
  • naru-plan — an advisory plan or implementation approach.
  • naru-impact — an advisory blast-radius / compatibility assessment.
  • naru-triage — an advisory bug or failure diagnosis.
  • naru-review — a dry-run review of a PR, branch, diff, or file. Never posted.

Ask naturally, or name one directly. They are not slash commands, run no fixed workflow, and grant nothing — an agent's permission map is the only thing that constrains what it does with the guidance.

06

Install

Requirements: OpenCode ≥ 1.18.4 and Node 24. Preview-before-mutation is the product's identity: every action that changes your machine shows exactly what it will do first.

Primary path · curl bootstrap 
curl -fsSL https://raw.githubusercontent.com/sean35mm/naru-opencode/main/bootstrap.sh | sh
naru install

The bootstrap downloads a checksum-verified release into ~/.naru and installs exactly one file — the naru command. It does not touch your OpenCode configuration; naru install does, and it previews every change and asks before applying anything. Restart OpenCode afterwards and pick naru-orchestrator in the agent picker (or opencode --agent naru-orchestrator).

The naru CLI

  • naru install — install into OpenCode; previews, then asks
  • naru upgrade — fetch the latest release, then install it
  • naru doctor — local install and configuration health
  • naru uninstall — preview removal, print the exact confirm command
  • naru rollback ID — restore a previous install transaction
  • naru version — installed vs. latest available
Alternative: clone + install.sh (what contributors use) 
git clone https://github.com/sean35mm/naru-opencode.git
cd naru-opencode
sh install.sh --preview   # the default; mutates nothing
sh install.sh --apply     # the only mutation boundary

Default target ~/.config/opencode; --project installs into .opencode, --dir PATH anywhere else. Markdown is symlinked so git pull keeps it current (--copy pins a snapshot — what release installs do). Installs write a .naru-install.json ownership manifest, skip unchanged assets, and back up only what they replace; --uninstall and --rollback ID also preview by default and require --apply plus a printed confirmation token.

Health check any time: naru doctor or node tools/naru-doctor.js --json — read-only, provider-free, contacts nothing.

07

Honest limits

Naru constrains Naru's own agents; it does not constrain the machine. Knowing where the walls end is part of trusting them.

Not a sandbox

It does not contain repository code, package scripts, or shell commands. A runner or writer executing your test suite runs whatever that suite runs.

Not a proof system

No formal guarantees. It is a permission map, a policy-and-evidence-gated review tool, and careful defaults — not verification. Not durable across processes, and not a global capacity meter.

Prompt policy is not enforcement

Checkpoints and scope discipline are instructions to a model. Mechanical boundaries are the permission maps, the posting tool's orchestrator-only schema validation and derived event gates, its one-POST/no-retry path, and worktree path containment.

Chain selection is startup-time, auth-based

The first authenticated chain entry is baked into a class's variants at plugin load — auth-based, not liveness-based. A model that fails at runtime is a failed child, not an automatic fallback; a class with no authenticated entry generates no variants at all.

Reserved variant namespace

naru-reader-*, naru-runner-*, naru-writer-* are Naru-managed names. Agents you hand-define under them can be shadowed or replaced on config load — and config edits take effect only after an OpenCode restart.

Isolation is containment, not protection

Isolated worktrees keep writers out of each other's way and require a clean repository. They do not protect against unrelated external mutation of the workspace.

08

Small glossary

orchestrator
The one visible, primary agent. Plans and delegates; cannot edit or run bash.
depth-1 topology
One root, leaf subagents. Every subagent has task: deny; grandchildren cannot exist. Breadth is unlimited.
dispatch
One subagent run via OpenCode's native task tool — on a base agent, or on a model-class variant when the model matters. Concurrent within a turn.
model class
A named entry in naru-runtime.json's models block: a short use plus an ordered chain of provider/model@effort entries. At startup each class becomes hidden variant agents (naru-reader-<class>, …) with the first authenticated chain entry baked in.
effort
A reasoning-effort token (low … max) attached to a chain entry and baked into the class's variants. Finer granularity means defining more classes.
the edit wall
Only naru-writer's frontmatter allows edit/apply_patch. OpenCode enforces it; no prose can change it.
scope / claim
The exact paths a writer is assigned. Claimed in Weaver before the first edit; conflicts requeue rather than prompt.
run / item
The units of naru-worktree: one run holds isolated per-writer items that the orchestrator integrates back.
dry-run review
The default review outcome: findings returned, nothing posted. Posting is a separate, explicitly requested act.
checkpoint
One stop naming the exact action, before anything destructive, irreversible, or scope-expanding.
lead, not proof
The trust level of the code graph. It says where to look; source code says what is true.
fail-closed
Readers with bash: deny and external_directory: deny — when in doubt, the answer is already no.
